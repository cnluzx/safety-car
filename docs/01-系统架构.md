# 系统架构

## 1. 机器人在赛场上要完成什么

比赛场地是一张 4×4 的网格道路图（代码里坐标范围 x: 0–3，y: 0–5），要求：

1. 从出发区 `START_AREA` 出发；
2. **覆盖全部道路**（不漏任何一段）；
3. 经过全部 12 个固定巡逻点（`N1`～`N12`）；
4. 途中遇到**绿色涵洞**（一共 8 个，位置随机）要停车侦查：抬起高位摄像头、左右扫视拍照、
   识别是否有人/持刀；
5. 遇到障碍物要绕行并重新规划；
6. 最后经 `J_TOP` 返回出发区，任务完成。

## 2. 两层分工

| | 上位机（香橙派 5 Pro / RK3588） | 下位机（ESP32-S3） |
| --- | --- | --- |
| 语言 | Python 3.10+ | C（ESP-IDF v5.5.2） |
| 职责 | 摄像头取帧、RKNN 推理、地图与路径规划、任务状态机、OLED、语音 | 电机 PWM、编码器读取、速度 PI、定距/定角闭环、舵机、串口协议、安全保护 |
| 实时性 | 20–30 FPS 视觉循环，几十毫秒级抖动可接受 | 10 ms 闭环周期，必须硬实时 |
| 崩溃影响 | 停车（下位机 1.5 s 失联保护兜底） | 车失控（但有急停与失联双保险） |

**关键设计**：所有"走多远、转多少度"的精确动作都在下位机用编码器闭环完成，上位机只发
"前进 100 个脉冲当量""原地转 90°"这类**语义指令**，然后等 `@` 应答。这样上位机即使
视觉掉帧、Python 卡顿，车的动作精度也不受影响。

## 3. 数据流

```
        ┌────────────── 巡线摄像头（低位，朝下看路面）
        │      │ 帧
        │      ▼
        │  line_detect.LineTracker  ── RKNN(pp544288) 道路分割 ──> ("LINE"/"CROSS", 偏差)
        │                                                              │
        │                                                              ▼
        │                                                    full_map_walk_test
        │                                                    （状态机 + 决策）
        ├────────────── 涵洞摄像头（高位，云台）
        │      │ 帧
        │      ▼
        │  Culvert_detect.CulvertBrightnessDetector ── 亮度/纹理 ──> "是不是涵洞"
        │      │ 触发侦查
        │      ▼
        │  yolo_detect.YoloDetector ── RKNN(2cls + 224 分类) ──> 有人/有刀
        │                                                              │
        │                                                              ▼
        │                                                    Serial.ChassisController
        │                                                      （@|code|v1|v2|v3#）
        └── RFID 读卡器 ──> odometry / navigator（位置锚定、节点确认）      │
                                                                          ▼
                                                                   ESP32-S3 下位机
```

三条并行线程（`full_map_walk_test.py` 里）：

| 线程 | 周期 | 作用 |
| --- | --- | --- |
| 巡线采集 `_road_processing_loop` | ~30 FPS | 取帧 → RKNN 分割 → 输出 `(road_type, offset)` |
| 涵洞采集 `_culvert_loop` | 按需 | 高位摄像头检测涵洞，命中时置事件 |
| 障碍检测 `_obstacle_loop` | 25 FPS | 画面下方 ROI 颜色突变 → 判定障碍 |
| RFID `_rfid_loop` | 50 ms | 读卡 → 通知导航器到达节点 |
| 主线程 | 20 ms | 状态机：读路况 → 决定巡线/路口动作/侦查/返航 |

## 4. 决策核心：拓扑图 + 覆盖规划

- `topo_map.py`：手工建图。节点是路口/固定点，边是路段，边上带**动作序列**
  （`FOLLOW_LINE` / `LEFT` / `RIGHT` / `FORWARD` / `U_TURN`）。
  物理赛道（`BASE_EDGES`）与"哪些边上有绿色涵洞"是分离的——涵洞位置每场随机。
- `navigator.py`：**全路段覆盖**规划。不是找最短路径，而是"把每条边都走一遍"，
  用 `_path_to_nearest_uncovered_edge()` 反复找最近未覆盖边，走完再返航。
  发现新涵洞时可以动态把该边标记为任务边。

这种"图上覆盖"而不是"固定路线"的设计，是为了应对**涵洞位置随机**：程序不需要提前知道
任务点在哪，走到哪发现哪。

## 5. 状态机（`FullMapWalkTest.run_mission`）

```
WAIT_READY ──> START_ALIGN ──> 主循环
                                ├─ road_type == "CROSS"  ──> _handle_crossroad()  （按图上动作序列执行）
                                ├─ road_type == "LINE"   ──> follow_once(offset)   （发 @|8 差速巡线）
                                ├─ 涵洞事件             ──> 停车 → @|10 触发侦查 → 收 Y_L/Y_R → 继续
                                ├─ 障碍事件             ──> _handle_pending_obstacle() → 重新规划
                                └─ 到 N12 且道路已覆盖完 ──> _run_return_start() → STOP
```

每个动作后都等 `@`（带 50 ms 最小延迟与 150 ms 去抖，防止上一动作的 `@` 被误认成这次的）。

## 6. 安全设计（三层）

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 硬件层 | 上电舵机归中、电机双低电平滑行停止 | `main.c: init_hw/set_motor` |
| 固件层 | 急停优先（不入队）、1500 ms 失联停车锁死、侦查期间锁电机、7 s 动作超时 | `main.c` 任务与 `link_watchdog` |
| 应用层 | 运行时健康检查（相机断流/道路推理断流）、连续丢帧上限、SIGINT 安全退出 | `full_map_walk_test.py: _runtime_health_error` |

应用层崩溃不会导致飞车：Python 一停发指令，下位机 1.5 s 后自动停车并锁死。
这条链路请在改动时务必保留。

## 7. 时间/精度现状（说实话）

- 巡线：视觉 PID 输出左右差速 → 下位机速度 PI 执行，`kp=0.5 kd=0.10 max_angle=30`（可调）。
- 定位：RFID 到点做绝对锚定；**编码器里程计代码完整但主流程没开启遥测**，所以位置估计实际未生效。
- 转弯：下位机按 `13 脉冲/度` 定角闭环，这个系数是实车标定的，换车必重新标定。
